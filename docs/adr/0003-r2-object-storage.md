# ADR-0003 — 車輛圖片用 R2 純物件儲存

- **日期**：2026-08-06
- **狀態**：已採納

## 背景

舊站把上傳的圖片存在 Web 主機檔案系統：`~/Upload/{Cars,Motors}/{VehicleID}/`，資料庫只存檔名。Workers 沒有可寫入的檔案系統，這個作法無法直接沿用。

## 決策

圖片存 **Cloudflare R2**（bucket `tsurumaru-media`，binding `BUCKET`），以自訂網域公開讀取。**不使用 Cloudflare Images 的即時變體轉換。**

物件 key：`vehicles/{vehicle_id}/{filename}` — 汽車與機車合併於同一前綴。

## 理由

1. **無 egress 費用。** 圖片是這個網站最大的流量來源，R2 不收流量費，成本可預測。
2. **搬遷是直接對映。** 舊的目錄結構本來就是 `{VehicleID}/{filename}`，資料庫也只存檔名。維持這個設計，資料庫欄位完全不用改，URL 在應用層組出即可。
3. **合併 Cars／Motors 前綴。** `vehicle_id` 是全域唯一 UUID，不需要用目錄區分車種。這讓上傳與讀取邏輯不必分岔，呼應[合併汽車與機車重複邏輯](../04-conventions.md#合併汽車與機車的重複邏輯)的整體方向。
4. **公開讀取走自訂網域，不經 Worker。** 圖片請求不消耗 Worker 用量，且自動走 Cloudflare 快取。

## 為什麼不做即時變體（明確選擇）

Cloudflare Images 的即時轉換能自動產生 WebP／AVIF 與各尺寸縮圖，效能上更好，但：

- 它是**額外的計費項目**，而本站的圖片數量與流量規模還不需要
- 前台版面必須零變更（[ADR-0004](0004-preserve-frontend-markup.md)），`<img>` 的 `srcset` 屬於「可改動範圍」的邊緣地帶，導入會擴大變更面
- 維持「上傳什麼就顯示什麼」與舊站行為一致，減少一個行為差異來源

**這是可逆決策。** 日後若圖片流量成為瓶頸，接上 Images 只需改 `src/lib/media.ts` 的 URL 組裝函式一處 — 這也是為什麼 URL 組裝必須集中在該模組，不得散落各頁面。

作為補償，上傳端**必須**在後台加上大小上限與尺寸建議，避免店員上傳原始相機檔。這不是預防性的顧慮 — 舊資料中僅有的兩張主圖，其中一張就是 **2.9 MB 的 JPEG**（[實測](../07-migration.md#來源)）。不做變體轉換就等於把這 2.9 MB 原封不動送給每一位訪客。

## 取捨

- 沒有自動最佳化，圖片大小取決於上傳者。以後台的上傳限制與教育緩解。
- R2 bucket 公開讀取後，只要知道 `vehicle_id` 與檔名即可取得圖片。這些圖片本來就是公開展示的商品照，可接受。
- 寫入**不**對外開放：不發放 R2 金鑰，一律經後台 endpoint 用 binding 寫入。

## 曾考慮

| 方案 | 未採用的原因 |
|---|---|
| R2 + Cloudflare Images 變體 | 額外費用；目前規模不需要；擴大前台變更面 |
| 圖片存 D1 為 BLOB | D1 單庫 500 MB 上限，且 BLOB 匯出不可靠 |
| 沿用舊主機的檔案系統 | Workers 無檔案系統；且無法退役舊主機 |
